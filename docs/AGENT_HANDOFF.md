# 모파고 · GitHub · 블로그 운영 인수인계 설명서

다른 에이전트가 대화 전체를 읽지 않고도 모파고 개발, 공개 저장소 관리, 블로그 소개 수정, Home 디자인과 유지보수를 이어갈 수 있도록 정리한 문서입니다. **사용자의 최신 요청을 먼저 확인하고, 실제 파일·원격 커밋·배포 결과를 대조한 뒤 작업하세요.**

작성 기준일은 **2026-10-03, Asia/Seoul**입니다. 이 문서는 당시 확인한 상태와 운영 절차를 설명합니다. 시간이 지나면 코드와 배포가 달라질 수 있으므로, 아래 수치나 상태를 확인 없이 현재 사실로 재사용하지 마세요.

**정본은 모파고 저장소의 `docs/AGENT_HANDOFF.md`입니다.** 블로그와 로컬 작업 폴더의 안내 파일은 이 정본을 찾는 진입점입니다. 여러 저장소에 설명서 전문을 복제해 서로 다른 내용으로 관리하지 않습니다.

## 빠른 시작

1. 이번 사용자 요청의 대상이 모파고, 블로그, PNGTuber 중 무엇인지 구분합니다.
2. 대상 저장소의 `AGENTS.md`, 이 문서, 관련 기능 문서를 읽습니다.
3. `git status`, `git remote -v`, 현재 브랜치와 원격 `main`을 확인합니다.
4. 필요한 파일만 수정하고 기능 검사·개인정보 검사·공개 파일 검사를 합니다.
5. 현재 요청 또는 대화에서 승인된 범위 안에서 커밋·게시합니다. 이미 받은 승인을 반복해서 묻지 않습니다.
6. 게시했다면 GitHub Actions와 실제 공개 페이지까지 확인합니다. 로컬 작성, 커밋, 푸시, 배포 성공은 각각 다른 상태입니다.

기존 제작 작업 공간에서는 아래 상대 경로를 사용합니다. 공개 문서에 개인 PC의 절대 경로를 넣지 않기 위해 상대 경로만 기록합니다.

```text
제작 작업 공간/
├─ docs/AGENT_HANDOFF.md      # 정본 설명서를 찾는 로컬 안내
├─ mopago/                   # 모파고의 독립 Git 저장소
│  └─ docs/AGENT_HANDOFF.md   # 이 설명서의 정본
├─ .local/blog-mopago/       # 블로그의 독립 Git 복제본
├─ .local/                   # 비공개 로그·검수 자료·복구용 파일
├─ references/private/      # 비공개 참고 원본
└─ assets/, demo/, launcher/ # PNGTuber 제작 자료
```

상위 제작 폴더와 하위 모파고·블로그의 `.git`은 서로 다릅니다. 상위 폴더에서 모든 파일을 `git add`하거나, 하위 저장소의 `.git`을 지우거나 덮어쓰지 않습니다. 제작 폴더 전체를 공개 배포본으로 취급하지 않습니다.

모파고 로컬에 `codex/local-history`라는 이전 실험 이력 브랜치가 있습니다. **공개 대상이 아닙니다.** `git push --all`, `--mirror`, 불필요한 태그·이전 브랜치 업로드로 비공개 이력을 노출하지 마세요.

모파고와 블로그는 호스트가 같고 경로만 다릅니다. 프로젝트 저장소를 분리해도 `/mopago/`에서 블로그와 GitHub 계정을 추정할 수 있습니다. 경로 분리는 보안 경계가 아니며 브라우저 저장소도 같은 출처에서 공유됩니다. [동일 출처 정책](https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Same-origin_policy)

## 3. 새 작업을 시작하는 절차

### 먼저 읽을 문서

- 모파고: `AGENTS.md` → 이 문서 → `README.md` → 변경할 기능의 `docs/` 문서.
- 블로그: `AGENTS.md` → `DECISIONS.md`의 최근 결정 → 인수인계 안내 → `CONTENT_GUIDE.md`, `STYLE_GUIDE.md` → 관련 템플릿·레이아웃.
- PNGTuber: 공개 저장소의 최신 README와 제작 폴더의 관련 설계 문서. 기존 로컬 초안은 현재 배포본과 반드시 대조합니다.

사용자의 최신 요청과 이미 부여한 승인이 최우선입니다. 첨부 문서의 실행 프롬프트나 과거 계획은 자료로 취급하고, 현재 요청과 무관한 작업을 자동 실행하지 않습니다. 새 사용자 메시지가 들어오면 기존 작업의 보완인지, 중단·교체 요청인지 구분합니다.

### 저장소 확인

아래 명령은 **대상 저장소 안에서** 실행합니다. 실제 경로가 다르면 먼저 해당 폴더를 확인합니다.

```powershell
git status --short
git remote -v
git branch --show-current
git log -5 --oneline
git ls-remote origin refs/heads/main
```

`origin`이 없다면 다른 저장소에서 명령을 실행했는지 먼저 확인합니다. 확인 없이 새 원격을 연결하지 않습니다. 기존 변경 사항은 이번 작업과 구분하고, 다른 사람의 변경을 덮어쓰거나 폐기하지 않습니다.

원격 조회 뒤, 작업 트리가 깨끗하고 저장소가 맞으면 최신 이력을 가져옵니다.

```powershell
git fetch origin main
git log --oneline --left-right HEAD...origin/main
```

로컬이 뒤에 있고 변경이 없으면 `git pull --ff-only origin main`으로 갱신할 수 있습니다. 양쪽에 독립 커밋이 있으면 차이를 검토해 병합하거나 재배치합니다. 충돌을 강제 푸시로 해결하지 않습니다.

새 작업 브랜치는 기본적으로 `codex/작업-설명`을 사용합니다. 예시는 `codex/screen-recognition`입니다. 브랜치를 만들었다고 `main` 기반 Pages가 배포되는 것은 아닙니다. 기존 승인된 게시 방식에 따라 검토 후 `main`에 반영하거나 PR을 사용합니다.

### 변경 시 반드시 지킬 동작

- 보드는 10열 × 16행이며 행별 10비트 정수로 표현합니다. 가로줄 제거 뒤 위 블록이 내려오지 않습니다.
- 블록 점유 상태와 능력 아이콘은 별도입니다. 채워진 칸 위에도 아이콘이 있을 수 있습니다.
- 조각 3개를 모두 사용해야 새 3개를 받습니다. 슬롯의 `ready`, `used`, `pending`을 구분합니다.
- 새 손패·교체 결과·새 아이콘 위치를 실제 결과처럼 임의 생성하지 않습니다. 웹에서 추천을 적용할 때 `draw:false`, `spawn:false`를 유지합니다.
- ‘다음 단계로 진행’은 보드 상단에 두고, 선택한 추천을 적용합니다. 첫 번째 추천만 고정 적용하지 않습니다.
- 초기화는 진행 중인 Worker와 예약 요청을 취소하고, 전체 상태와 되돌리기 기록을 지운 뒤 초기 상태를 자동 저장합니다. 늦게 도착한 이전 추천을 표시하지 않습니다.
- JSON 파일 저장·불러오기 기능은 없습니다. 브라우저 자동 저장 키 `mopago.state.v1`은 별개이며, 상태 형식을 바꾸면 복원·마이그레이션을 검토합니다.
- 이용자 화면에는 보드·조각·보유 능력·진행 상황·다음 수 등 이용 기능만 둡니다. 학습 패널, 모델 비교, 개발 로그, 홍보용 설명, 저장소 유지보수 문서를 앱 화면에 추가하지 않습니다.
- 로그인·원격 보드 업로드·분석·광고 기능은 현재 없습니다. 도입하려면 별도 요구와 설계가 필요합니다.

회전·반전 좌표와 조각 표기는 [규칙 문서](RULES.md)를 기준으로 합니다. `ㅡ`는 3×1, `ㅅ`은 3×2로 사용자 확인을 받았으며, `ㅋ`, `ㅂ`도 카탈로그에 포함합니다. 조각 이름·순서 변경은 저장 상태의 ID 호환성에 영향을 줍니다.

### 확인된 규칙과 가정

점수·능력 출현 규칙은 `docs/RULES.md`가 출처를 구분합니다. 단계별 공식 조각 확률 수치는 확인되지 않았습니다. 현재 가정은 다음과 같습니다.

```text
단계 s = 1..5, 조각 칸 수 k = 1..10
r(s) = 0.6 ^ ((s - 1) / 4)
w(s, k) = r(s) ^ ((10 - k) / 9)
P(조각 i | s) = w(s, k_i) / 모든 조각 가중치의 합
```

단계 경계는 누적 제거 줄 0~30 / 31~60 / 61~100 / 101~150 / 151 이상입니다. 첫 단계의 시작 가중치만 동일하며, 별도의 균등가정 모델은 없습니다. 공식 규칙을 새로 확인하면 출처·확인일·변경 내용을 기록하고 [확률표](PROBABILITIES.md)와 환경 서명·평가를 함께 갱신합니다.

일반 조각 7회 배치마다 아이콘을 생성하고, 종류는 점 찍기 40%·바꿔 뽑기 60%, 보유 능력 합계 최대 7개·보드 아이콘 최대 3개를 반영합니다. 아이콘 위치 분포 등 미확정 규칙을 사실로 확정하지 않습니다.

## 5. 모델 개선과 화면인식 후속 개발

이 절은 **앞으로 검증할 개발 방향**입니다. 현재 완료 기능을 설명하는 절이 아닙니다.

### 탐색 엔진 개선

현재 정책은 21개 특징의 선형 가치함수와 빔 폭 12·최대 3행동 탐색입니다. Cross-entropy 방식으로 정책 가중치를 최적화했으며, 대형 신경망·AlphaGo 구조라고 소개하지 않습니다.

개선 후보는 현재 3조각의 배치 순서를 더 넓게 탐색하고, 후보별로 미래 손패·능력 출현을 여러 번 모의하는 방식입니다. MCTS나 확률을 고려하는 탐색을 비교할 수 있습니다. 능력 사용도 탐색에 포함하고, 임의 미래 추첨을 알고 있는 것처럼 추천하지 않습니다.

평가는 다음 조건을 맞춥니다.

1. 기존·신규 엔진에 같은 게임 규칙과 분포, 비교용 시작 시드, 계산 시간 예산을 적용합니다.
2. 학습·후보 선택과 최종 평가를 분리합니다. 최종 평가를 보고 다시 선택했다면 새로운 평가 집합이 필요합니다.
3. 평균·P90·최고·50만 점 이상 횟수·게임 수·제한 종료 수·한 수 계산 시간을 기록합니다.
4. 브라우저와 평가 CLI가 같은 추천 함수를 쓰는지 확인합니다. 더 강한 비공개 평가 엔진 결과를 가벼운 웹 엔진 성능으로 표시하지 않습니다.
5. 시뮬레이션 분포와 실제 게임 분포의 차이를 함께 설명합니다. 50만 점 도달을 보장하지 않습니다.

기존 평가 CLI에는 평가 시드 3개가 고정되어 있습니다. 그 평가 결과를 후보 선택에 활용했다면, 새 독립 평가를 위해 시드 설정을 명시적으로 바꿔 기록해야 합니다.

### 화면인식 개발 순서

1. **정지 화면 인식:** 게임 영역과 10×16 격자를 보정하고, 보드 점유·아이콘·조각·능력 개수·지운 줄 수를 읽습니다.
2. **수동 정답과 대조:** 채워진 보드, 아이콘이 있는 보드, 능력 보유 화면, 회전·반전된 조각, 사용한 슬롯을 포함합니다.
3. **실시간 연결:** 사용자가 화면 연결 버튼을 누르고 게임 창을 선택합니다. 화면 공유 권한은 매 연결 시 필요합니다. [화면 캡처 API](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getDisplayMedia)
4. **안정화와 검증:** 여러 프레임을 비교하고, 애니메이션·마우스 가림·창 이동·배율 변화를 처리합니다. 낮은 확신의 칸이나 숫자는 표시하고 수정을 받습니다.
5. **추천과 연결:** 검증된 최신 관측 상태로 추천을 계산합니다. 화면 상태가 바뀌면 이전 추천을 취소합니다.

고정 UI는 먼저 색상·격자·도형 비교와 숫자 OCR을 검토합니다. 등록한 19종 조각의 모든 회전·반전 모양과 대조하고, 조각 색상 하나에만 의존하지 않습니다. 능력 아이콘은 블록 점유와 별도로 읽습니다.

화면을 읽는 기능과 게임에 클릭·키 입력을 보내는 기능은 다릅니다. 현재 후속 요구는 **인식과 추천**이며 자동 조작 기능을 포함하지 않습니다.

원본 화면은 기본적으로 서버에 업로드하거나 저장하지 않고 필요한 게임 영역만 브라우저에서 처리하는 설계를 우선합니다. 이용자가 제공한 화면에는 개인 계정·대화 등이 섞일 수 있으므로 공개 샘플로 자동 사용하지 않습니다. 필요한 검증 자료도 공개 허용 범위를 먼저 확인합니다.

최초 제공 화면은 빈 보드·능력 0개인 상태였습니다. 이것만으로 실제 블록·아이콘 인식 정확도가 검증됐다고 표시하지 않습니다. 화면인식 도입 시 수동 수정 기능과 기존 수동 입력 경로를 유지합니다.

## 6. GitHub 저장소 작성·커밋·게시

### 기존 프로젝트와 신규 저장소 구분

모파고와 PNGTuber는 이미 독립 공개 저장소가 있습니다. 기능 추가를 이유로 동명 저장소를 새로 만들거나 기존 이력을 초기화하지 않습니다.

사용자가 별도 신규 프로젝트 공개를 요청한 경우에는 다음 순서를 사용합니다.

1. 대상 계정과 저장소 이름, 공개 범위, 라이선스 결정 여부를 확인합니다.
2. 공개할 소스·필수 에셋·문서·검사·배포 파일의 허용 목록을 만듭니다.
3. 비공개 제작 이력이 섞였으면 선별한 파일을 깨끗한 별도 폴더에 복사합니다. `.git`, 참고 원본, 로그, 구모델을 복사하지 않습니다.
4. GitHub에서 Owner와 이름을 확인해 저장소를 만듭니다. 준비된 Git 이력을 올릴 때는 README 등을 원격에서 별도 자동 생성해 이력을 갈라 놓지 않습니다.
5. 검수한 파일만 첫 커밋에 포함하고, 사용할 브랜치만 올립니다.
6. README·Pages·블로그 소개 링크를 실제 생성한 주소로 연결합니다.

라이선스는 자동으로 통일하지 않습니다. 모파고 코드는 MIT이고, PNGTuber 에셋의 재배포 라이선스는 별도 결정이 필요합니다. [GitHub 신규 저장소 안내](https://docs.github.com/en/repositories/creating-and-managing-repositories/creating-a-new-repository)

### 커밋 전 검토

```powershell
git diff --stat
git diff --check
git diff
git ls-files
git config user.name
git config user.email
```

커밋 작성자 이름은 허용한 공개 이름 BH CHOI, 이메일은 본인 GitHub 설정에서 확인한 비공개 noreply 주소를 사용합니다. 원래 연락처나 Windows 계정명을 넣지 않습니다. 계정별 noreply 값은 추측하지 않습니다.

이번 변경의 파일을 **명시적으로** 스테이징합니다. 예를 들어 모파고 사용 안내 변경은 아래처럼 처리합니다.

```powershell
git add README.md docs/AGENT_HANDOFF.md
git diff --cached --stat
git diff --cached --check
git diff --cached
```

파일 목록은 실제 변경 범위에 맞게 바꿉니다. 아직 추적되지 않은 파일도 별도로 확인합니다. `.gitignore`를 추가했다고 이미 추적된 비공개 파일이나 과거 커밋이 제거되는 것은 아닙니다.

커밋 메시지는 변경 결과를 설명합니다. PR을 만들면 문제와 최종 동작, 검증 결과를 중심으로 작성하고 현재 작업에 연결합니다. 긴 본문은 구조화된 도구 입력 또는 실제 줄바꿈이 있는 본문 파일을 사용합니다.

### 인증과 원격 반영

브라우저 GitHub 로그인, Git Credential Manager, 연결 앱의 쓰기 권한은 서로 다릅니다. 브라우저에 로그인했다고 API의 403이 자동으로 해결되는 것은 아닙니다.

- 기존 정상 Git 인증이나 해당 저장소에 쓰기 권한이 있는 연결 도구를 사용합니다.
- 자격 증명 출력, 토큰이 포함된 원격 URL·명령행·로그를 남기지 않습니다.
- 인증 오류라면 재로그인 또는 저장소 권한을 정확히 요청합니다. 승인이 이미 있는 게시 작업을 다시 승인받는 문제와 구분합니다.
- 작업 범위에 승인된 게시가 없다면 코드·문서·검증을 먼저 준비하고, 게시가 마지막 승인 단계가 되도록 합니다.

정상 게시에서는 확인한 대상 브랜치만 푸시합니다. `main` 게시가 승인되고 준비됐을 때의 예시는 `git push origin main`입니다. 비공개 브랜치까지 올리는 `--all`·`--mirror`는 사용하지 않습니다.

블로그 `AGENTS.md`는 원격 게시·Pages 설정 변경 등에 명시적 승인을 요구합니다. 사용자가 이미 승인한 범위는 이어서 진행하되, 새 파괴적 작업이나 범위 확대에는 그 승인을 재사용하지 않습니다. 과거 개인정보 정리의 강제 푸시 승인은 일상 유지보수의 승인이 아닙니다.

## 7. 모파고 검사와 GitHub Pages 배포

### 로컬 개발

Node.js 20 이상을 사용합니다. 현재 앱에는 외부 npm 패키지 설치가 필요하지 않습니다. 모파고 폴더에서 실행합니다.

```powershell
npm start
```

개발 주소는 `http://127.0.0.1:8878/`입니다. 서버 종료는 Ctrl+C이며, 이미 같은 포트를 쓰면 기존 작업인지 확인한 뒤 처리합니다. 다른 프로그램을 무작정 종료하지 않습니다. `file://`로 HTML을 직접 열면 모듈·Worker·모델 로딩을 검증할 수 없습니다.

### 변경 종류별 검사

| 변경 | 필요한 확인 |
| --- | --- |
| 설명서·README만 수정 | 링크·문서와 코드 일치·개인정보·`git diff --check` |
| UI·상태 처리 | `npm test`, 빌드, 실제 브라우저의 해당 조작 |
| 게임 규칙·조각 | 규칙 검사, 상태 호환성, 모델 서명, 재평가 |
| 추천·모델·분포 | 규칙 검사, 웹과 CLI 동일성, 후보와 분리한 평가 |
| 공개 파일 추가 | 빌드 허용 목록과 개인정보·메타데이터 검사 |

```powershell
npm test
npm run build
```

빌드 스크립트는 프로젝트 내부의 정해진 `dist/`만 재생성합니다. 다른 경로를 지우도록 수정하지 않습니다. 결과에는 `index.html`, `.nojekyll`, 배포별 `releases/` 아래 앱·스타일·아이콘과 `models/default.json` 하나만 포함합니다. `.local`, 테스트 실행 결과, 문서는 앱 배포물에 넣지 않습니다.

새 런타임 모듈이나 OCR 자산을 추가하면 `scripts/build.mjs`의 명시적 파일 목록도 갱신해야 합니다. 개발 서버에서만 정상이고 Pages에서는 파일이 404인 상태로 배포 완료를 선언하지 않습니다.

### 모델 후보 검증

현재 CLI 예시는 다음과 같습니다. 전체 평가·학습은 CPU 시간이 많이 드는 작업이며 문서 수정만 할 때는 실행할 필요가 없습니다.

```powershell
npm run train -- 30 24 16
npm run tune
npm run evaluate -- .local/expert-candidate.json 500
npm run finalize
```

`train` 인수는 반복 횟수·후보당 게임 수·후보 수입니다. `evaluate`의 500은 시드당 게임 수이므로 현재 3개 시드에서는 총 1,500게임입니다. 후보와 원시 결과는 `.local/`에 남깁니다.

`finalize`는 현재 형식에서 10,000게임 이상으로 집계 가능한 정책 탐색, 동일 정책·엔진 해시의 1,500게임 이상 평가, 제한 종료 0게임을 확인합니다. 평균·P90 목표 통과 자체를 강제하는 절차는 아니므로, 목표 미달이면 그대로 공개 판정합니다. 신형 탐색 엔진의 형식이나 목표를 바꾸면 이 검사와 문서도 함께 설계합니다.

P90은 점수를 정렬해 `ceil(0.9 × N)`번째 값을 고르는 방식입니다. 상위 10%의 평균이 아닙니다. 기존 고정 평가 시드를 반복해 후보 선택에 쓰면 별도 평가로 부를 수 없습니다.

### Pages 배포

현재 `.github/workflows/pages.yml`은 `main` 푸시 또는 수동 실행으로 동작합니다. Node.js 22에서 검사·빌드 후 `dist/`를 게시합니다. 권한은 `contents: read`, `pages: write`, `id-token: write`이며, 실행 번호를 자산 버전에 사용합니다.

기존 Pages 설정은 유지합니다. 새 저장소에 처음 설정할 때만 승인 범위에서 Settings → Pages → Source를 GitHub Actions로 정합니다. [Pages 게시 소스 안내](https://docs.github.com/en/pages/getting-started-with-github-pages/configuring-a-publishing-source-for-your-github-pages-site)

배포 완료 확인은 다음 순서입니다.

1. 원격 `main`이 의도한 커밋인지 확인합니다.
2. 해당 SHA의 `Deploy Mopago to Pages` 실행에서 build·deploy가 성공했는지 확인합니다.
3. 공개 앱의 HTML이 새 `releases/` 주소를 가리키고 모델·Worker가 정상 응답하는지 확인합니다.
4. 조각 입력 → 추천 표시 → 선택한 추천으로 다음 단계 → 되돌리기를 검사합니다.
5. 능력 사용과 새 손패·교체 결과 대기를 확인합니다.
6. 초기화 뒤 새로고침해도 이전 보드·능력·조각·추천이 복원되지 않는지 확인합니다.
7. 좁은 화면에서 보드·슬롯이 넘치지 않고 키보드 조작이 가능한지 확인합니다.

## 8. 블로그 글 작성과 프로젝트 소개 갱신

### 콘텐츠를 넣을 위치

| 성격 | 폴더 | 원칙 |
| --- | --- | --- |
| 공개 결과물·독립 저장소가 있는 프로젝트 | `_projects/` | 정식 소개와 저장소·데모 링크 |
| 연구 내용 | `_research/` | 연구 형식과 출처 |
| 학습·작업 노트 | `_notes/` | 과정과 배운 점 |
| 취향·게임 기록 | `_posts/` | Play 글, 필요한 고정 주소 유지 |

모파고는 프로젝트입니다. 소개를 수정할 때 **`_projects/mopago.md`만 갱신**합니다. 사용자가 이미 삭제한 중복 포스트를 다시 만들지 않습니다. 기존 `play/mopago/index.html` 이동 안내는 공유된 주소를 보존하는 파일입니다.

### 모파고 소개의 실제 필드

```yaml
---
title: "한글 모아모아 알파고 · 모파고"
subtitle: "수동 보드 입력과 학습 기반 다음 수 추천"
date: 2026-10-01 19:00:00 +0900
tags:
  - Projects
  - Play
  - Game
  - Machine-Learning
repository_url: "https://github.com/cbh456746/mopago"
demo_url: "https://cbh456746.github.io/mopago/"
---
```

이는 기준일의 실제 필드입니다. 화면인식이나 새 탐색을 배포하면 구현 결과에 맞게 subtitle·본문·태그를 검토합니다. 구현 전 계획을 현재 기능처럼 바꾸지 않습니다.

소개글은 무엇을 하는 도구인지, 핵심 조작 3~4개, 사용 주소·저장소, 성능 해석에 필요한 한계를 짧게 설명합니다. 확률표·모델 수치·설치 절차 전문은 모파고 README와 `docs/`에 둡니다. 같은 상세 내용을 블로그에 복제해 수치가 서로 어긋나게 만들지 않습니다.

### 글 작성 규칙

- 새 문서는 해당 `templates/` 파일을 참고합니다. 템플릿의 예시 제목·날짜·빈 섹션을 그대로 게시하지 않습니다.
- 게임 관련 콘텐츠에는 `Play`와 `Game`을 함께 넣습니다. 프로젝트는 `Projects`, 연구는 `Research`, 노트는 `Notes`도 붙입니다.
- 일반 `Blog` 태그는 사용하지 않습니다. 기존 표기인 `Machine-Learning`, `Data-Science` 등을 재사용합니다.
- 새 검색 태그가 필요하면 `_data/tag-index.yml`과 Archive 동작을 확인합니다.
- 날짜는 Asia/Seoul 기준이며 필요하면 `+0900`을 명시합니다. `_config.yml`의 `future: false` 때문에 미래 날짜 글은 보이지 않을 수 있습니다.
- 제목 다음에 목적을 먼저 설명하고, 본문은 짧은 문단·필요한 표·순서 있는 절차로 구성합니다. 빈 제목과 더미 링크는 남기지 않습니다.
- 본문 변경은 사용자가 승인한 수정 범위 안에서 합니다. 관련 없는 기존 글을 전면 개작하지 않습니다.
- 이미지·영상은 검수한 공개용 파일만 사용합니다. 이미지에는 내용이 드러나는 alt를 쓰고, 원본 파일명·개인 경로를 그대로 노출하지 않습니다.

블로그 내부 링크는 `relative_url`·`absolute_url` 등 기존 Liquid 규칙을 따릅니다. 기존 공개 주소를 바꾸는 경우 변경 대상과 이동 안내, 검증 결과를 URL 기록에 남깁니다.

### 앱 변경과 소개 갱신 순서

먼저 앱 구현·검증·배포를 끝내고 실제 사용 주소를 확인합니다. 그다음 소개가 현재 공개 기능을 설명하도록 수정합니다. 앱 배포가 실패했다면 소개에는 완료 기능으로 쓰지 않습니다.

기능이나 모델 공개 시 함께 검토할 문서는 다음과 같습니다.

| 바뀐 내용 | 함께 확인할 문서 |
| --- | --- |
| 이용 방법 | 모파고 README, 필요할 때 블로그 소개 |
| 규칙·조각 | RULES, ARCHITECTURE, 모델 서명·검사 |
| 분포 | PROBABILITIES, README, LEARNING, EVALUATION |
| 정책 성능 | default.json 집계, EVALUATION, LEARNING, README, 이 문서의 상태 표 |

| 유지보수 결정 | 해당 저장소 AGENTS/설명서, 블로그 DECISIONS·TASKS의 관련 항목 |

## 10. 블로그 검증·배포·RSS

### 구성과 검사

블로그는 Jekyll 기반 정적 사이트입니다. 모파고의 `npm run build`를 여기서 실행하지 않습니다.

```powershell
npm run validate
git diff --check
```

`scripts/validate-content.mjs`는 front matter, 태그, 필수 파일, 일부 프로필 규칙을 확인합니다. 개인정보 전체 검사나 현재 Resume 두 항목 제한을 완전히 보장하는 검사는 아닙니다. 생성된 HTML과 수정 파일을 별도로 확인해야 합니다.

Ruby·Bundler 환경이 준비된 경우 로컬 Jekyll 빌드를 사용할 수 있습니다.

```powershell
bundle install
bundle exec jekyll build
```

개발 서버는 `bundle exec jekyll serve`입니다. 실행 환경이 없다고 관련 없는 런타임을 임의 설치하거나 빌드 성공을 주장하지 않습니다. 소스 검사를 마친 뒤 기존 GitHub Actions의 Jekyll 빌드로 확인할 수 있습니다.

현재 `.github/workflows/pages.yml`은 `main` 푸시·수동 실행 시 콘텐츠 검사 → Jekyll 빌드 → 생성된 RSS XML 검사 → Pages 업로드·배포를 수행합니다. 해당 커밋의 build·deploy가 모두 성공했는지 확인합니다.

### 공개 페이지 확인

| 주소 | 확인할 내용 |
| --- | --- |
| `/` | Hanasaka·사진·유지할 링크·삭제한 설명문 부재 |
| `/resume/` | 승인된 이름·Education 두 항목 |
| `/projects/`, `/projects/mopago/` | 모파고 소개·저장소·데모 링크 |
| `/play/` | 중복 모파고 소개 포스트 부재 |
| `/play/mopago/` | 정식 Projects 소개로 이동 |
| `/research/`, `/notes/`, `/archive/` | 메뉴·목록·태그 탐색 |
| `/search.json` | 유효한 검색 자료·삭제한 개인정보나 중복 소개 부재 |
| `/feed.xml` | XML 파싱, 공개 항목·중복·링크 |

Jekyll의 `exclude`는 **사이트 빌드** 제외입니다. `docs/`와 유지보수 MD가 HTML로 배포되지 않아도 Public Git 저장소에서는 누구나 읽을 수 있습니다. `.gitignore`와 개인정보 검수도 따로 필요합니다.

### RSS의 현재 동작과 보류 사항

`feed.xml`은 posts·projects·research·notes를 합쳐 날짜순 최신 20개를 RSS로 만듭니다. 현재 description에는 HTML을 제거한 **본문 내용**이 들어갑니다. 제목·날짜·링크만 제공하는 형태는 아직 적용하지 않았습니다.

`_config.yml`에 `RSS: false`가 있지만, 현재 `_includes/footer.html`의 RSS 링크는 이 값과 관계없이 출력됩니다. 이 설정값만 보고 RSS가 숨겨졌다고 판단하지 마세요. feed 파일 자체도 생성됩니다.

XML 오류를 수정할 때는 생성 결과의 XML 선언 앞에 공백이 생기지 않도록 합니다. 검사 대상은 Liquid가 섞인 원본이 아니라 생성된 `_site/feed.xml`입니다.

```powershell
python -c "import xml.etree.ElementTree as E; r=E.parse('_site/feed.xml').getroot(); assert r.tag=='rss' and r.find('channel') is not None; print('RSS XML OK')"
```

현재는 사용자 중단 요청에 따라 RSS 동작을 유지합니다. 이후 숨김이 승인되면 footer·피드 자동 발견 링크·파일 공개 여부를 각각 확인해야 합니다. 링크를 숨기는 것은 접근 통제가 아니며, 이미 공개한 자료의 회수를 의미하지 않습니다.

| --- | --- |
| 실제 기능 소스, 재현에 필요한 검사·빌드 코드 | 임시 출력, 미사용 개발 스크립트, 실패 후보 |
| 배포 모델 하나와 집계된 평가 정보 | 중간 가중치, 구모델, 개별 게임 보드·점수 로그 |
| 필요한 사용·설계·운영 문서 | 개인 PC 경로, 인증 기록, 비공개 복구 자료 |
| 검수한 최종 에셋·공개 허용 예제 | 참고 원본, 권리·공개 여부 미확인 이미지·영상 |
| 허용된 공개 이름·GitHub 저장소 링크 | 원래 연락처, 개인 식별값, 토큰·키·비밀번호 |

검사 소스는 유지보수에 필요한 코드입니다. 불필요한 테스트 결과물과 혼동해 전부 삭제하지 않습니다. 반대로 필요한 검사 파일이라는 이유로 실제 사용자 상태나 비밀값을 fixture에 넣지 않습니다.

### 변경마다 확인할 순서

1. `git status --short`, `git diff`, `git diff --cached`로 이번 수정과 공개 파일 목록을 확인합니다.
2. 개인 이름·연락처·PC 경로·토큰·키·대화 기록·삭제된 더미 정보가 없는지 검사합니다. 삭제한 개인정보 원문을 공개 검수 보고서에 다시 적지 않습니다.
3. 새 이미지·영상·실행 파일이 있으면 EXIF·XMP·IPTC·작성자·원래 경로·디버그 경로 등의 메타데이터도 확인합니다.
4. `.gitignore`와 사이트 빌드 허용 목록을 확인합니다. 제외 파일이 이미 추적됐는지도 확인합니다.
5. 생성된 HTML·JSON·RSS·번들·다운로드 파일과 실제 공개 응답을 확인합니다.
6. 필요하면 이번 커밋의 작성자·메시지·과거 파일 노출도 확인합니다.

텍스트 패턴 검사는 보조 수단입니다. 경고가 없다고 개인정보가 없다고 보장하지 않으며, 정상 URL·GitHub noreply 같은 허용 값의 오탐도 사람이 검토합니다. 넓은 검사에서 찾은 민감 문자열을 도구 출력이나 공개 이슈에 그대로 붙이지 않습니다.

### Git 이력 정리의 범위

블로그는 사용자 승인으로 과거 개인정보가 포함된 접근 가능한 `main` 이력을 교체한 적이 있습니다. 이 작업은 이전 커밋 ID를 바꾸며, 오래된 복제본·브랜치·태그·PR 참조가 오염된 이력을 다시 유입시킬 수 있습니다.

이력 교체 후에는 오래된 복제본을 무작정 병합하지 않습니다. 검수한 미게시 변경을 별도로 보존하고 정화된 원격에서 새로 복제하거나 안전하게 재동기화합니다. 현재 트리에서 파일을 지우는 것과 모든 과거 노출을 제거하는 것은 다릅니다.

당시 특정 이전 SHA의 자료가 원격 API에서 계속 조회되는 것도 관측했습니다. GitHub 캐시·포크·다른 사람의 복제본·검색엔진까지 삭제가 완료됐다고 주장하지 않습니다. 복구용 bundle과 이전 원본 이력은 비공개 보관합니다. [GitHub 민감 정보 제거 안내](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository)

후속 이력 재작성·강제 푸시·저장소 삭제·공개 범위 변경이 필요하면 대상 참조, 파일 트리 보존, 복구 방법, 외부 사본의 한계를 설명하고 그 작업에 대한 승인을 받습니다. 이전 D-015 승인을 새 작업의 일반 승인으로 사용하지 않습니다.

비밀키나 토큰 유출이라면 이력에서 지우는 것만으로 끝나지 않습니다. 폐기·재발급 필요성을 확인하고 승인된 계정 절차로 처리합니다. 현재 문서 작성 자체가 계정 설정 변경 요청은 아닙니다.

### 호스팅과 공격 위험을 다룰 때

현재 모파고는 정적 앱으로 서버 측 실행·로그인·사용자 업로드 API가 없습니다. 이를 서버나 공급망 위험이 전혀 없다는 뜻으로 설명하지 않습니다. GitHub 계정·Actions 권한·외부 의존성·DOM 입력 처리·브라우저 저장소 접근을 변경할 때 관련 위험도 검토합니다.

같은 `github.io` 출처에서 다른 자체 앱과 함께 운영되므로 저장소 분리만으로 블로그를 숨길 수 없습니다. 사용자 입력 표시에는 기존의 `textContent` 등 안전한 방식을 유지하고, 외부 데이터를 그대로 `innerHTML`에 넣지 않습니다.

동시 접속 수·DDoS 방어·트래픽 용량을 임의 숫자로 보장하지 않습니다. 필요한 시점에 [GitHub Pages 제한](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits), 실제 전송 크기와 호스팅 조건을 확인해 계산합니다. 정적 호스팅에 없는 서버 보안 설정을 적용했다고 주장하지 않습니다.

## 12. 오류 대응과 복구

| 증상 | 먼저 확인 | 처리 원칙 |
| --- | --- | --- |
| GitHub 403 | 인증한 계정, 대상 저장소 쓰기 권한, 사용한 연결 경로 | 로컬 결과를 보존하고 권한 문제를 정확히 보고 |
| 브라우저는 로그인인데 Git은 실패 | Git 자격 증명과 앱 연결 권한 | 브라우저 로그인만으로 해결됐다고 추정하지 않음 |
| `origin` 없음 | 현재 폴더와 `.git`, `git remote -v` | 잘못된 저장소에 원격을 만들지 않음 |
| push 거부·이력 분기 | 원격 변경, 이전 정화 이력과의 관계 | fetch·차이 검토, 강제 푸시로 우회하지 않음 |
| Pages 실패 | 해당 SHA의 실패 단계·로그 | 소스나 설정의 원인을 수정한 뒤 다시 확인 |
| 배포 성공인데 화면이 예전 것 | 원격 SHA·HTML 자산 버전·CSS 캐시·이전 서비스워커 | 캐시 원인과 미배포를 구분 |
| 모파고 추천 실패 | pending 슬롯, 모델 서명, Worker와 JSON 응답 | 입력 오류·호환 오류·파일 404를 구분 |
| 초기화 뒤 옛 추천 표시 | 타이머, 요청 ID, 이전 Worker | 오래된 결과를 무시하고 초기화 상태 저장 |
| 블로그 글이 안 보임 | 날짜·시간대·future, 컬렉션, front matter | 템플릿 예시 날짜나 폴더를 확인 |
| RSS XML 오류 | 생성 결과의 선언 위치·문자 이스케이프 | 피드 삭제 대신 생성 원인 수정 |
| 검사 도구·런타임 없음 | 변경에 꼭 필요한지, 기존 Actions 검사 가능 여부 | 미검증 범위를 기록하고 성공으로 표시하지 않음 |

Windows에서 재귀 삭제·이동을 한다면 최종 절대 대상이 의도한 작업 폴더 안에 있는지 먼저 확인하고, PowerShell의 `-LiteralPath`를 사용합니다. 다른 셸로 경로를 넘겨 문자열 명령으로 일괄 삭제하지 않습니다. `git reset --hard`, `git clean -fd`, 전체 변경 폐기 역시 일상 복구 수단으로 사용하지 않습니다.

공개된 기능을 되돌릴 때는 일반적으로 이전 변경을 취소하는 새 커밋을 만들고 검사·재배포합니다. 이것은 Git 이력 자체를 재작성하는 작업과 다릅니다. 모델을 되돌리면 모델 서명과 엔진·분포·평가 문서가 함께 맞아야 합니다.

권한 제한이나 자동 승인 검토가 작업을 거부하면 수행한 검사·준비 결과를 보존합니다. 남은 단계와 거부 이유를 설명하고, 필요한 경우 그 단계에 한정해 승인이나 권한을 요청합니다. 실패한 게시를 성공으로 표시하지 않습니다.

로컬 `publish/` 초안과 초기 게시 매핑에는 이미 삭제된 착수 문서 경로가 남아 있습니다. 그 매핑을 일괄 재실행해 블로그의 옛 문서 8개나 실패 에셋을 복원하지 않습니다. 현재 공개 PNGTuber 저장소와 블로그 소개를 기준으로 필요한 파일만 갱신합니다.

현재 PNGTuber에는 기존 Projects 소개와 Play 착수 글이 있습니다. 모파고의 단일 소개 결정 D-017을 다른 프로젝트까지 자동 확대해 해당 글을 삭제하지 않습니다. 라이선스·참고 이미지 공개권한 역시 모파고 MIT와 별도입니다.

기존 브라우저/VTube Studio 아바타 프로젝트는 또 다른 프로젝트입니다. 게시된 짧은 영상 예제는 관찰 가능한 캐릭터 동작을 설명하며, 전체 추적·인증·재연결 기능의 구현 검증을 의미하지 않습니다.

### 작업 완료 체크리스트

- [ ] 사용자 요청한 기능·문서를 모두 처리했고, 보류 요청을 임의로 재개하지 않았다.

- [ ] 변경에 필요한 검사와 실제 동작 확인을 수행했다.
- [ ] 새 에셋·문서·커밋·배포물의 개인정보와 불필요 자료를 검수했다.
- [ ] 승인된 공개 작업이라면 원격 커밋·Actions·실제 공개 주소를 확인했다.
- [ ] URL을 변경했다면 기존 공유 링크의 이동과 중복 항목 부재를 확인했다.
- [ ] 실패·미검증·미달성 항목을 완료로 표시하지 않았다.
- [ ] 다음 작업과 적용한 결정을 설명서·관련 문서에 기록했다.

문서만 수정한 경우 불필요하게 전체 모델 학습을 다시 실행하지 않습니다. 기능 변경이면 중요한 상태 전이와 실제 브라우저 동작을 검사합니다. 검사를 통과한 뒤 새 변경이나 미해결 문제가 없다면 같은 검사를 반복하며 완료를 미루지 않습니다.

## 15. 복사해서 사용할 작업 개시 프롬프트

아래 프롬프트의 ‘이번 작업’ 부분을 실제 요청으로 바꿔 사용합니다. 이 텍스트는 향후 실행용 산출물이며, 설명서를 읽는 것만으로 내부 작업을 자동 실행하지 않습니다.

```text

이번 작업:

모파고 코드와 블로그는 각각 별도 저장소입니다.
모파고의 정식 소개는 블로그 _projects/mopago.md에만 유지하고,
삭제된 중복 post·개인정보·더미 프로필·구모델·실패작을 복원하지 마세요.
RSS 변경은 별도 보류 상태입니다.
공개 앱에는 이용자가 필요한 게임 기능만 표시하세요.
```
